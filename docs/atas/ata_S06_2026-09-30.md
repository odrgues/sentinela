## Decisões Tomadas
- Critério do CP-2 confirmado com o professor: pelo menos 2 endpoints CRUD, conexão com o banco do CP-1 funcionando, testes manuais demonstrados, tratamento básico de erros (200/201/400/404/500) e documentação da API. Não é mais exigido CRUD de 2 entidades completas, como constava na leitura anterior do cronograma.
- `git pull` trouxe o backend da Larissa: projeto Spring Boot em `src/backend`, com CRUD completo de `Usuario` (`POST`, `GET`, `PATCH`, `DELETE` em `/api/usuario`) — 4 endpoints, acima do mínimo de 2.
- **Bug corrigido antes da apresentação:** a dependência `spring-boot-starter-security` (usada só para o `BCryptPasswordEncoder`) ativava autenticação HTTP Basic em todas as rotas, com senha gerada aleatoriamente a cada start. Isso derrubava qualquer chamada com `401 Unauthorized`, inclusive numa demonstração ao vivo. Criado `SecurityConfig` liberando todas as rotas — autenticação de verdade é escopo do CP-4, não do CP-2.
- Adicionado tratamento de erro genérico (`500`) no `GlobalExceptionHandler`, complementando o `400`/`404` que a Larissa já tinha implementado.
- Testes manuais executados via `curl` contra a API local, confirmando todos os status esperados e a persistência real no MySQL do CP-1 (consulta direta à tabela `usuario` depois de cada operação):

| Operação | Status obtido | Esperado |
|---|---|---|
| Criar usuário | 201 | 201 |
| Consultar usuário existente | 200 | 200 |
| Atualizar usuário (PATCH parcial) | 200 | 200 |
| Remover usuário | 204 | 204 |
| Consultar usuário removido | 404 | 404 |
| Criar com e-mail inválido | 400 | 400 |
| Criar com e-mail duplicado | 400 | 400 |

- Documentação criada em `docs/especificacao_api.md` (rotas, parâmetros, corpo de requisição/resposta, códigos de status) e coleção `docs/insomnia_cp2.json`, importável no Insomnia, com os 7 casos testados acima.
- README atualizado com a seção do backend (como rodar a API, endpoints disponíveis).
